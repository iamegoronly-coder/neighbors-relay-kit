# Комплект реле «Соседей»

[English](README.md) · [Русский](README.ru.md) · [Deutsch](README.de.md)

Комплект для своего публичного [Nostr](https://github.com/nostr-protocol/nips)-реле **«Соседей»**, чата в Home Bills. Основан на наших встроенных реле: [strfry](https://github.com/hoytech/strfry) за Caddy, короткий срок хранения, лимиты ресурсов и гибридный TLS. Сайт приложения в комплект не входит. Обновление от 21 октября 2026 уменьшает лимит события до 60 KiB и убирает дублирующий полный обход базы; оба встроенных реле уже работают с этими исправлениями. Новый тестовый кандидат — `v0.1.0-test.4`. Старые теги и архивы сохранены без изменений. Установка этого кандидата на новом чистом VPS пока не проверена: прежний тестовый VPS удалён.

Цель первого выпуска — **отдельный чистый VPS с Ubuntu 24.04 x86_64**. ARM64, Debian и автоматическая установка рядом с существующим Caddy — отдельные следующие этапы; для существующего сервера используйте ручную инструкцию.

> **Статус.** Комплект разворачивает реле, но не меняет настройки клиентов автоматически.
> Для подключения своего реле нужна сборка приложения с поддержкой выбора собственных реле.
> Репозиторий и тестовые релизы пока приватные; состояние публикации описано ниже.

[Аудит границ реле/клиента и результаты проверок (2026-10-21, EN)](docs/relay-client-audit-2026-10-21.md).

## Что реле видит и чего не видит

Реле хранит и раздаёт подписанные события Nostr. Содержимое сообщений приложение шифрует сквозным
шифрованием до отправки; реле не может его прочитать и не пытается (`content` не разбирается и не пишется в журнал).

| Реле видит | Реле не видит |
|---|---|
| IP-адреса и время подключений | Текст, фото, голос, имена в сообщениях |
| Внешние ключи и теги событий: у личного конверта (kind 1059) одноразовый внешний ключ и ключ получателя на реле в теге `p` | Постоянный ключ личности отправителя внутри личного конверта (это не гарантирует анонимность отправителя) |
| Размер событий и `created_at` (у личных конвертов сдвинут случайно на ±15 мин) | Расшифрованный список контактов и читаемую историю переписки |

Реле может связать поступившее событие с соединением, IP, временем и тегами получателя, а также
наблюдает фильтры подписок. Сопоставление этих данных может раскрывать связи и активность;
одноразовый внешний ключ не делает отправителя анонимным. Утверждения о конфиденциальности
относятся к корректно зашифрованным личным конвертам приложения. Публичное реле принимает и
другие события, включая открытый текст и публичные записи приложения; оно их не шифрует.

`OK` от реле означает «принято на хранение», а не «доставлено». Удаление события из LMDB не
гарантирует физического стирания байтов, а у хостинга могут быть снимки диска. Не обещайте
пользователям гарантированного удаления.

### IP-адреса в этой конфигурации

Caddy принимает подключения и видит IP клиентов. strfry слушает loopback; при `realIpHeader = ""`
его собеседник — Caddy (`127.0.0.1`), а переданные прокси заголовки с IP клиента не используются.
В примере Caddyfile не включён HTTP access-log, strfry работает с уровнем WARNING без дампов
событий. Это уменьшает обычное журналирование, но **не гарантирует, что IP нигде не записываются**:
отдельно существуют ошибки и runtime-журналы Caddy, журналы хоста/провайдера и изменения оператора.

### Аутентификация

NIP-42 AUTH **по умолчанию выключен**; на обоих встроенных реле ничего не меняется. Test.4 содержит `setup.sh --auth` для новой установки
пользовательского реле. Перед включением для пользователей нужны совместимый выпуск приложения
и проверка кита на чистом VPS. В приложении уже есть внутренняя поддержка
custom-маршрутизации и NIP-42; видимый выбор реле ещё не выпущен.

С `--auth` мастер до запуска strfry задаёт `enabled = true`, `serviceUrl = "wss://<domain>/relay"`,
`restrictedReadKinds = "1059"` и `restrictReadToInvolvedPubkey = true`. Выбор сохраняется;
последующий `--check` требует NIP-42 в NIP-11. Это проверка объявления возможности, а не контроля
доступа; ограничения проверяет интеграционный тест настоящего сервера. Клиент подтверждает владение
**отдельным ключом inbox этой пользовательской сети**, а не Bluetooth-личностью, и повторяет
закрытую подписку после соответствующего подтверждения AUTH. Отказ завершает попытку без
автоматического цикла переподключений.

Читать kind 1059 может аутентифицированный участвующий ключ: получатель из `p` или внешний автор
события. Запись остаётся публичной: любой может отправить правильно подписанный конверт на чужой
`p`; что принять, решают сквозные проверки приложения. Другие kinds этот флаг не ограничивает.
AUTH не скрывает метаданные от оператора. Фильтры подписок и раньше показывали запрашиваемые ключи
inbox; AUTH дополнительно подтверждает владение ключом и связывает его с подключением. Caddy видит
его IP. Обычное журналирование не меняется.

**Пользовательское реле обслуживает прямую интернет-доставку: шлюзы и курьеры недоступны как с AUTH,
так и без него.** Ограничение обеспечено кодом; будущая настройка должна показывать предупреждение.
Bluetooth и обычная Bluetooth mesh-доставка сохраняются. Делегирования ключа шлюзу нет.
См. [протокол проверок AUTH](docs/custom-relay-auth-2026-10-21.md) и
[NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md).

До выпуска переключателя приложению нужен подписанный обмен адресами inbox с привязкой к выбранной сети: custom-режим сейчас отключает старые BLE/групповые адреса без scope. Внутренние тесты доставки с известными адресами не проверяют обнаружение на устройствах.

### Типы событий

| Kind | Для чего в «Соседях» |
|---|---|
| 1059 | Личные конверты (схема gift wrap, шифрование на основе bitchat): личные и групповые сообщения, медиа, квитанции. Приложение подписывается на свой `#p` |
| 30078 | Записи приложения по NIP-78 (например, статус приёма сообщений автору) |
| 1401, 20000, 20001 | «Соседи» их сейчас не публикуют; реле принимает их для совместимости с bitchat (курьерские конверты, эфемерные и геоканалы), smoke-тест их проверяет |

## Политика и лимиты

- **История:** обычное событие принимается, если `created_at` не старше 26 ч и не более чем на 20 мин
  в будущем; выдаётся и хранится до `created_at + 26 ч`, очистка — каждые 2 минуты.
  Приложение запрашивает конверты примерно за последние 24 ч, поэтому 26 ч — запас, а не
  обещание доставки: устройство, выключенное больше суток, пропустит сообщения на любом реле.
- **Эфемерные kinds 20000–29999:** принимаются в пределах ±60 с от часов реле, на диске — технический
  буфер 90 с от `created_at`; встроенная очистка по индексу запускается примерно каждые 9 с.
  Обычно это 90–99 с для события с текущей датой, до ~160 с от получения с допустимым
  опережением часов на 60 с; нагрузка и простой могут увеличить срок. Это не офлайн-почта.
- **NIP-40 `expiration`:** уже истёкшие отклоняются; истёкшие отсекаются при чтении (патч strfry)
  и физически удаляются встроенной очисткой по индексу истечения. Внешний таймер каждые
  2 минуты выполняет только `delete --age 93600`; его отметка успеха проверяет удаление
  старой истории, а не исправность встроенного cron.
- **NIP-42 AUTH выключен по умолчанию.** В текущих исходниках есть опциональное ограничение чтения на пользовательском реле; см. раздел об аутентификации. Запись и лимиты ресурсов не меняются.

| Лимит | Механизм |
|---|---|
| 1 vCPU, 512 MiB RAM, 64 задачи, 256 дескрипторов | systemd `CPUQuota`, `MemoryMax`, `TasksMax`, `LimitNOFILE` |
| 100 WebSocket-соединений | `relay.maxConnections` (точный, по патчу) и Caddy `unhealthy_request_count` (ранний 503) |
| База < 1,5 GiB и > 2 GiB свободно на её разделе | `strfry-disk-guard` перед стартом и каждую минуту; останавливает только реле |
| Событие ≤ 60 KiB (61 440 байт), сообщение WebSocket ≤ 128 KiB | `events.maxEventSize`, `relay.maxWebsocketPayloadSize` |
| 20 подписок на соединение, 500 событий на фильтр, 1 MiB исходящего буфера | `strfry.conf` |
| Журнал реле ≤ 50 MiB / 7 дней, в памяти | namespace `journald@strfry.conf`; тела событий, ключи и теги не пишутся |

Лимит соединений — не rate limit по IP, а guard проверяет диск раз в минуту: всплеск внутри минуты,
насыщение сети и авария хоста вне его зоны.

## Постквантовый TLS

Caddy 2.10+ по умолчанию предлагает гибридный обмен ключами `X25519MLKEM768` (X25519 + ML-KEM-768).
При фактическом согласовании гибрида обмен ключами рассчитан на защиту от известных классических
и квантовых атак, включая «сохранить сейчас, расшифровать потом». Apple включает поддержку в
`URLSession` на iOS/macOS 26, но версии ОС и сервера сами по себе не подтверждают алгоритм
конкретного соединения. Старые клиенты могут согласовать классический X25519.
Защита заканчивается на сервере, завершающем TLS. Она не делает существующее сквозное шифрование
приложения постквантовым и не защищает сохранённые конверты от самого реле.

`scripts/install.sh` не запустится со старым Caddy (`bin/require-pq-caddy`), а
`scripts/check-pq-tls.sh <домен>` проверяет оба обмена ключами снаружи, доверие к сертификату,
имя сервера и код завершения OpenSSL. Нужны Python 3 и OpenSSL 3.5+; каждый процесс ограничен
15 секундами (параметр `--timeout`). Проверка версии Caddy — предварительное условие;
фактическую поддержку подтверждает внешнее рукопожатие.

## Требования

- Ubuntu 24.04 x86_64 (проверенная платформа); для работы реле хватает 1 vCPU / 1 GiB RAM.
  Сборке strfry нужно около 2,5 GiB памяти (на маленьком VPS добавьте swap) и время.
- Не меньше 4 GiB свободно на разделе `/var/lib/strfry` (1,5 GiB на базу + 2 GiB резерва).
- Домен с A/AAAA-записью на сервер (без CDN-прокси, если не уверены, что он пропускает WebSocket),
  открытые TCP 80 и 443, порт 7777 **не** открыт наружу.
- Точные часы (NTP): события оцениваются по `created_at`.

## Два пути развёртывания

Можно собрать реле из исходников или установить готовый бинарник; конфигурация, службы и
установщик у обоих вариантов общие. Для независимой проверки предусмотрена каноническая
Docker-сборка с закреплёнными инструментами и побайтное сравнение с опубликованным файлом.
Обычная сборка средствами Ubuntu тоже остаётся доступной, но при других версиях компилятора
и библиотек её SHA-256 может отличаться.

Подробности: [оба пути установки и проверка](docs/deployment.ru.md). Есть приватные тестовые Release; подпись выпуска пока не настроена. Для чистого VPS добавлен локальный мастер `setup.sh`: он настраивает
зависимости, Caddy, домен, реле и таймеры. Установщик сохраняет проверенные байты бинарника без изменений.
Две чистые локальные сборки уже совпали побайтно: [протокол проверки](docs/reproducibility-check-2026-10-15.ru.md).
Проверка на независимой машине ещё предстоит.

## Установка

**Статус:** репозиторий и Release остаются приватными. Эти HTTPS-команды без авторизации подготовлены для будущей публикации; сейчас без доступа к репозиторию они завершатся ошибкой (обычно HTTP 404). Они не меняют приватность. `v0.1.0-test.4` — тестовый выпуск, а не рекомендация для рабочего сервера.

Для **чистого VPS с Ubuntu 24.04 x86_64**, systemd и синхронизацией NTP. Заранее направьте домен на VPS и откройте TCP 80/443. Для готового файла нужно около 1 ГиБ RAM и минимум 4 ГиБ свободно на `/var/lib`.

Нужны `curl`, `ca-certificates`, `tar`, `sha256sum`, Python 3 и sudo/root; для исходников также Git. Если инструменты скачивания/клонирования отсутствуют, установите их один раз:

```sh
sudo apt-get update && sudo apt-get -o DPkg::Lock::Timeout=600 install -y ca-certificates curl git
```

Если вы вошли под root, команды можно выполнять без `sudo`.

1. Скачайте архив закреплённой версии в новый временный каталог:

```sh
relay_work=$(mktemp -d -t neighbors-relay.XXXXXXXX) &&
curl --fail --show-error --location --proto '=https' --proto-redir '=https' \
  --output "$relay_work/neighbors-relay-v0.1.0-test.4.tar.gz" \
  https://github.com/iamegoronly-coder/neighbors-relay-kit/releases/download/v0.1.0-test.4/neighbors-relay-v0.1.0-test.4.tar.gz
```

2. В той же SSH-сессии проверьте закреплённую сумму, затем распакуйте архив и запустите мастер:

```sh
(cd "${relay_work:?Run the download command first}" &&
  printf '%s  %s\n' '9774069b863188a9cdbe599a33da2ae4029f75fba2a88a424b1a328a091499d8' 'neighbors-relay-v0.1.0-test.4.tar.gz' | sha256sum --check - &&
  tar -xzf neighbors-relay-v0.1.0-test.4.tar.gz &&
  cd neighbors-relay && sudo sh setup.sh)
```

Мастер спросит язык, домен и способ установки, затем покажет план для подтверждения. Для готового файла выберите **1**. После публикации GitHub CLI и токен не нужны. Архив остаётся в `$relay_work`; при ошибке HTTP или несовпадении суммы сначала устраните причину. Проверенные распакованные скрипты можно изучить до запуска `sudo sh setup.sh`. В README исходного тега/архива замените `COPY_SHA256_FROM_TEST_4_RELEASE_NOTES` на SHA-256 архива из описания выпуска test.4. README ветки main закрепляет сумму после упаковки: архив не может содержать собственную контрольную сумму. Это не цифровая подпись выпуска.

### Клонирование и сборка исходников

После публикации можно клонировать тот же конкретный тег по HTTPS и выбрать сборку. Сейчас приватный репозиторий по-прежнему требует доступа. Используйте новый каталог; существующее реле мастер не заменяет.

```sh
git clone --branch v0.1.0-test.4 --single-branch \
  https://github.com/iamegoronly-coder/neighbors-relay-kit.git neighbors-relay-source
```

```sh
(cd neighbors-relay-source && sudo sh setup.sh --mode source)
```

В режиме source мастер скачает закреплённые исходники и соберёт реле вместо использования готового бинарника. Нужно минимум 2,5 ГиБ RAM + swap и 6 ГиБ свободно на `/var/lib` и `/opt` (6 ГиБ всего, если это один раздел). Обычная сборка средствами Ubuntu может дать другой хеш; для побайтного сравнения используйте каноническую Docker-сборку.

### Ручная установка

Для опытных операторов, которым нужны отдельные шаги. От root на сервере, из закрытой копии репозитория (например, `/root/neighbors-relay`).

1. **Caddy 2.10+** из официального репозитория — [docs/caddy.md](docs/caddy.ru.md#new-server).
2. **Сборка strfry** закреплённого commit с патчем ([docs/patch.md](docs/patch.ru.md)):
   ```sh
   sh scripts/build-strfry.sh
   ```
3. **Назовите реле** в `config/strfry.conf` (`info.name`, `description`, `contact`) и установите
   сервис, вспомогательные скрипты и таймеры:
   ```sh
   sh scripts/install.sh
   ```
4. **Опубликуйте через Caddy.** Скопируйте `config/Caddyfile.example` в `/etc/caddy/Caddyfile`
   (или добавьте его блок сайта в существующий файл), замените `relay.example.org`, затем:
   ```sh
   caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
   systemctl reload caddy
   ```
5. **Проверьте.**
   ```sh
   /usr/local/libexec/strfry-health                      # healthy: true
   curl -fsS -H 'Accept: application/nostr+json' https://relay.example.org/relay
   curl -s -o /dev/null -w '%{http_code}\n' https://relay.example.org/metrics   # 404
   ```
   С машины с OpenSSL 3.5+ (на Mac — Homebrew OpenSSL):
   ```sh
   sh scripts/check-pq-tls.sh relay.example.org          # две строки PASS
   ```
   По желанию — внешний приёмочный тест (Python 3.12, `websockets==15.0.1`, `coincurve==21.0.0`).
   Для каждого запуска задайте новый файл-манифест: существующий файл не перезаписывается.
   ID попыток публикации сохраняются на диск **до** отправки, в том числе при потере ACK или
   падении теста. Удаление ID отклонённых событий безвредно.
   ```sh
   RELAY_HOST=relay.example.org python3 tests/smoke_test.py initial --manifest /tmp/relay-smoke-run.jsonl
   ```
   Скопируйте манифест в закрытый каталог целевого сервера и выполните:
   ```sh
   /usr/local/libexec/strfry-cleanup-smoke-events --manifest /root/relay-smoke-run.jsonl --relay wss://relay.example.org/relay
   /usr/local/libexec/strfry-cleanup-smoke-events --manifest /root/relay-smoke-run.jsonl --relay wss://relay.example.org/relay --execute
   ```
   Проверьте точные ID в пробном прогоне. Используйте только манифесты собственных запусков;
   URL должен совпадать с манифестом и локальной базой нужного реле. Поиск по текстовому префиксу
   не используется. Сохраняйте манифест до успешной очистки; повреждённый файл отклоняется целиком.

## Обслуживание

```sh
systemctl status caddy strfry.service strfry-prune.timer strfry-disk-guard.timer --no-pager
/usr/local/libexec/strfry-health
journalctl --namespace=strfry -u strfry.service -u strfry-prune.service --since '1 hour ago' --no-pager
sudo -u nostr-relay /usr/local/bin/strfry --config /etc/strfry/strfry.conf --verbosity=WARNING info
```

`strfry-health` выводит только агрегаты (активность, локальные метрики, соединения, размер базы,
свободное место, память, последняя очистка, таймеры, NTP) и возвращает ненулевой код при проблеме.
Он рассчитан на пути и порт этого комплекта (`/var/lib/strfry`, `127.0.0.1:7777`).

- Изменили настройки реле: `systemctl restart strfry.service` (Caddy не трогается).
- Изменили Caddy: сначала `caddy validate …`, затем `systemctl reload caddy`.
- **Если guard остановил реле**, не запускайте его вслепую: проверьте место и базу, затем
  `systemctl start strfry.service`.

## Обновление

- **Caddy:** плановое, с резервной копией и откатом — [docs/caddy.md](docs/caddy.ru.md#upgrading).
- **strfry:** патч привязан к закреплённому commit. Новая версия upstream — это пересмотр и повторная
  проверка патча, отдельная сборка, сохранение прежних бинарника и конфига и замена только бинарника
  при остановленном реле. Никогда не запускайте старый и исправленный бинарники на одной базе и не
  используйте плавающий `latest`. Подробности — [docs/patch.md](docs/patch.ru.md).

Вывести реле из работы без удаления данных: убрать его блок из Caddyfile, `caddy validate`, reload,
затем `systemctl disable --now strfry.service strfry-prune.timer strfry-disk-guard.timer`.
`/var/lib/strfry/db` автоматически не удаляется.
