# Два способа установки и независимая проверка

[English](deployment.md) · [Русский](deployment.ru.md) · [Deutsch](deployment.de.md)

Оба способа используют один комплект настроек, вспомогательных скриптов и systemd-служб.
Различается только происхождение исполняемого файла: пользователь собирает его сам или
скачивает из конкретного выпуска. Само реле работает от `nostr-relay`, установка требует root.

**Статус:** репозиторий и Release остаются приватными. Эти HTTPS-команды без авторизации подготовлены для будущей публикации; сейчас без доступа к репозиторию они завершатся ошибкой (обычно HTTP 404). Они не меняют приватность. `v0.1.0-test.2` — тестовый выпуск, а не рекомендация для рабочего сервера.

**Проверки:** test.1 скачан из приватного Release, проверен по SHA-256 и установлен на чистый VPS с Ubuntu 24.04; внешние проверки TLS и WebSocket прошли. Test.2 содержит исправленную диагностику места и прошёл локальные тесты, но ещё не устанавливался на чистый VPS. Настройка собственного реле в интерфейсе приложения пока в планах; у реле нет AUTH, подключиться может любой знающий адрес.

[Быстрый старт](quickstart.ru.md)

## Подготовка для ручной установки

Нужны Ubuntu 24.04 x86_64, домен на сервер, доступные TCP 80/443 и не менее 4 ГиБ свободного места.
Для работающего реле достаточно 1 vCPU / 1 ГиБ RAM. Компиляцию лучше выполнять на отдельной машине.

Сначала клонируйте конкретный выпуск комплекта. В следующем примере `REPOSITORY_URL` и
`RELEASE_TAG` нужно заранее заменить опубликованными значениями:

```sh
git clone --branch "$RELEASE_TAG" --single-branch "$REPOSITORY_URL" neighbors-relay
cd neighbors-relay
```

Прочитайте установщик и конфигурацию. Настройте Caddy по [инструкции](caddy.ru.md#new-server),
установите библиотеки на сервер реле:

```sh
sudo apt-get -o DPkg::Lock::Timeout=600 install -y --no-install-recommends \
  python3 git curl liblmdb0 libssl3t64 zlib1g libsecp256k1-1 libzstd1 libstdc++6
```

Заполните имя и контакт оператора в `config/strfry.conf`. После любого из вариантов ниже
опубликуйте домен через Caddy и выполните проверки из [README](../README.ru.md#установка).
Низкоуровневый `scripts/install.sh` не меняет firewall и Caddyfile, не создаёт swap и отказывается перезаписывать уже
существующую службу реле.

## Вариант 1: самостоятельная сборка

Для сравнения с официальным бинарником используйте закреплённую Docker-сборку. На отдельной
машине сборки нужны Docker, не менее 3 ГиБ доступной RAM и около 6 ГиБ места на образ и исходники.
На маленьком сервере, где будет работать реле, Docker не нужен.

Из клонированного репозитория:

```sh
docker build --platform linux/amd64 --file build/Dockerfile \
  --output type=local,dest=./out .
```

Скрипт скачивает исходники strfry и подмодули закреплённых версий, применяет открытый патч
и компилирует программу. Готовое реле в процессе сборки не скачивается. Образ Ubuntu закреплён
по digest, версии пакетов — в `build/packages.lock`; также закреплены параметры компиляции,
путь сборки, локаль, поведение генераторов Perl и способ получения Git-версии.

Скачайте опубликованный бинарник того же выпуска отдельно в `downloaded/strfry`, не запуская
его, и сравните файлы:

```sh
python3 scripts/compare-binaries.py out/strfry downloaded/strfry
```

Команда требует Python 3.11+ и только читает файлы. `IDENTICAL: every byte matches` означает
полное побайтное совпадение. При отличии она завершается с ошибкой: нельзя утверждать, что
файлы идентичны, пока причина отличия не выяснена.

Перенесите собранный файл на сервер реле. Из клонированного комплекта на этом сервере:

```sh
sudo sh scripts/install.sh --binary /путь/к/собранному/strfry \
  --sha256 "$EXPECTED_SHA256"
```

`EXPECTED_SHA256` — заранее проверенная контрольная сумма сравниваемого выпуска.
Установщик сначала создаёт временную копию, проверяет её SHA-256 и архитектуру, затем
устанавливает именно эти байты. Дополнительного `strip`, меняющего файл, при установке нет.

Обычная сборка средствами Ubuntu тоже доступна:

```sh
sudo sh scripts/build-strfry.sh
sudo sh scripts/install.sh
```

Она использует текущие версии пакетов Ubuntu и может дать другой SHA-256. Для побайтной
проверки выпуска нужен именно закреплённый рецепт, приведённый выше.

## Вариант 2: готовый бинарник

Клонируйте и изучите тот же выпуск комплекта. Скачайте `strfry` и метаданные из конкретного
GitHub Release. Получите ожидаемый SHA-256 из независимой сборки или аутентифицированной
записи выпуска, затем выполните:

```sh
python3 scripts/verify-binary.py /путь/к/скачанному/strfry --sha256 "$EXPECTED_SHA256"
sudo sh scripts/install.sh --binary /путь/к/скачанному/strfry --sha256 "$EXPECTED_SHA256"
```

Контрольная сумма рядом с файлом защищает от повреждения относительно опубликованного
значения. Она не защищает от злоумышленника, который смог заменить и файл, и сумму.
Подпись помогает проверить автора выпуска, но для неё нужен заранее установленный источник
доверия. В текущем черновике ключ подписи не настроен; файлы нельзя называть подписанными.

## Проверка двух VPS

На каждом сервере:

```sh
sha256sum /usr/local/bin/strfry
```

Для одного канонического выпуска ожидаются одинаковые суммы. Можно также скопировать оба
файла на одну машину и сравнить их командой `compare-binaries.py`.

Одинаковый бинарник не означает полностью одинаковую среду: сравнивайте также тег комплекта,
патч, вспомогательные скрипты, службы, версии системных библиотек и Caddy. Домен, контакт
оператора, TLS-сертификаты и данные базы закономерно различаются. Не копируйте приватные
ключи и переписки ради сравнения серверов.

Побайтное совпадение — проверяемое свидетельство соответствия бинарника исходникам и среде
сборки. Оно не доказывает отсутствие уязвимостей, доверенность компилятора или то, что чужой
сервер действительно запускает этот файл и не ведёт дополнительные журналы.

## Ограничения и публикация

- Две чистые локальные сборки — только локальная проверка воспроизводимости. До публикации
  нужен повтор на независимой машине и проверка обоих путей установки на чистых VPS.
- Для повторной компиляции без повторного скачивания компилятора используйте разные
  `--build-arg BUILD_RUN=first` / `--build-arg BUILD_RUN=second` и отдельные каталоги вывода.
  Меняется именно этап сборки; готовые объектные файлы предыдущего запуска не используются.
- Если закреплённая версия пакета исчезнет из Ubuntu-репозитория, сборка остановится. Нельзя
  незаметно подменить её новой и обещать тот же результат. До обещания долгосрочной
  воспроизводимости нужно архивировать пакеты сборки или закрепить доступный снимок Ubuntu.
- Вместе с бинарником нужно опубликовать полный использованный исходный код с подмодулями
  (`source.tar.gz`), патч, GPL-лицензию, `packages.lock`, `build-info.txt`, `SHA256SUMS`,
  исходники самого комплекта и результаты проверок.
- Тестовый VPS был установлен предыдущей обычной сборкой. Эти изменения его не обновляют;
  его старый SHA-256 не обязан совпадать с новым каноническим выпуском.
