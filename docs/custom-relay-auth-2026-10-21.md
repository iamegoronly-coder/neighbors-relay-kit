# Optional custom-relay AUTH — 21 October 2026

Status: implemented in the current source tree, **after immutable v0.1.0-test.3**.
No production relay was changed. The client implementation is not yet an App Store release;
the user-facing custom-relay selector is still pending. Deploy to users only after a compatible
client and a newly packaged/validated kit are available. Do not replace existing release assets.

## Contract

- Standard configuration remains AUTH-off. The fresh-host wizard accepts `--auth` in both
  binary and source mode, including read-only `--plan`.
- Before starting strfry it writes `auth.enabled = true`, canonical
  `serviceUrl = "wss://<domain>/relay"`, `restrictedReadKinds = "1059"`, and
  `restrictReadToInvolvedPubkey = true`. It preserves file ownership/mode and other settings.
- The installation state records the choice. `setup.sh --check` restores it and checks for
  NIP-42 in NIP-11. An explicit `--check --auth --domain …` also requires that advertisement.
  `--check` does not enable AUTH or prove the policy by itself.
- This is a fresh-install feature, not an in-place migration of an existing relay.
- Restricted reads admit the recipient's inbox key or the event's outer author key. AUTH
  proofs use kind 22242 and the AUTH command, never EVENT storage. Writes remain public.
- The client uses a separate relay identity scoped to the chosen custom network, signs the
  challenge and exact canonical WSS URL, and retries its closed inbox after the matching OK.
  Built-in sockets never receive this identity. No alternate-relay fallback is introduced.
- Challenge/session state is connection-local. Negative ACKs, repeated auth-required after a
  retry, restricted responses, a fifth distinct challenge, or a 15-second unanswered AUTH
  deadline terminate the attempt without an automatic auth reconnect loop. Ordinary network
  recovery is unchanged. strfry's actual `ERROR: auth-required:` prefix is handled explicitly.

**Product boundary:** custom relays have direct Internet delivery, but no gateway or courier
operation. This applies with or without AUTH. Ordinary Bluetooth/mesh remains available.
The future relay selector must explain this before switching. AUTH does not hide operator-visible
metadata or prevent unwanted writes. Filters already expose requested inbox keys; AUTH additionally
proves key ownership and binds it to the connection. Caddy sees the connection's IP address.

## Validation

- `sh tests/run-unit-tests.sh`: **65 tests PASS**, plus shell syntax. Wizard tests cover default/off and opt-in configuration,
  configuration already present at service start, permissions, saved-state checks, missing NIP-42,
  read-only plan, and EN/RU/DE catalog completeness. Binary runtime dependencies no longer include
  git/binutils; source-build tooling remains installed by the source-build script.
- `tests/test_auth_integration.py --binary /path/to/strfry`: PASS against the canonical Linux
  amd64 strfry and temporary LMDB, in a disposable container with external network disabled.
  The configuration is generated by the actual wizard. NIP-11 advertises 42; anonymous and
  foreign inbox reads are denied, including broad/mixed filters. The owner can read its stored
  events and receive new ones. An anonymous broad live subscription receives no private events.
  Bad challenge, wrong service URL, forged signature and proof replay on a different connection
  are refused. AUTH is absent from the database. Anonymous writes remain accepted.
- The same canonical binary passes `tests/test_integration.py` with default AUTH-off configuration:
  event/frame boundaries, 200-event replay plus EOSE, expiry, pruning with live subscriptions,
  connection slots and slow readers.
- App commit `f7ed084`: **244 tests / 24 suites PASS**. The focused Swift relay/session/routing
  suite verifies signatures and identity scope,
  ACK/CLOSED orderings, stale proofs, bounded challenges, canonical URLs, and lifecycle cleanup.
  Counts and invocation are recorded in the application's `TESTING.md`.

The real-server integration uses synthetic Python clients. Swift protocol/state tests are separate;
this is not a physical Apple-device or TLS end-to-end AUTH acceptance run.

## Release follow-up

The old test VPS was deliberately removed; new clean-VPS tests are deferred by the maintainer.
Do not infer real systemd/TLS installation success from container tests. Before public release,
package a new immutable candidate containing these changes, update all six README/quickstart
references together, run binary and source installations on fresh VPSs, remove synthetic events,
and verify anonymous downloads after publication is approved.

ARM64, Debian and automatic integration with an existing Caddy remain separate follow-up stages.
The supported first-release target stays a dedicated Ubuntu 24.04 x86_64 VPS. This limitation is
now visible near the start of all three READMEs.
